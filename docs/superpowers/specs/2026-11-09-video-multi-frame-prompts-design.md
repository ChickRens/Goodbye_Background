# 動画切り抜き: 複数フレームへの点の指定（設計）

- 日付: 2026-11-09
- 状態: オーナー承認済み（チャットで設計 1〜5 を承認。方式 A・上限 5 枚・手動で選ぶ）
- 関連: `docs/superpowers/specs/2026-11-05-video-cutout-design.md`（元の仕様）、`docs/video-cutout-measurements.md`（ダーツの動画での見失い）

## 1. 目的

編集されたミーム動画には場面の切り替え（カット）が入る。カットの直後は人物の大きさ・向きが急に変わり、SAM2 が被写体を見失う
（ダーツの動画でカットの後の 15 フレーム = 0.5 秒、人物が丸ごと消えた）。また、ダンスで腕を激しく振る所は、
small でもブレで腕が欠けることがある。

利用者が**開始位置以外のフレームにも点を打てる**ようにし、そのフレームで被写体を捉え直させる。

成功の基準:
- カットのある動画で、カットの少し後のフレームに点を打つと、そこから先で見失わない
- 腕が欠けたフレームに点を打つと、そのフレーム（とその後）で腕が残る
- 点を打ったどのフレームでも、プレビューで見た範囲 = 出力のそのフレーム（CLAUDE.md の約束事 16）

## 2. 決めたこと（オーナー）

| 項目 | 決定 |
|---|---|
| フレームの選び方 | **手動**。プレビューの画面で動画を好きな位置に動かし、そのフレームに点を打つ（カットの自動検出はしない） |
| 1 本あたりの上限 | **5 枚**（開始位置を含む） |
| ワーカーでの使い方 | **方式 A**: 追跡がそのフレームに来た時点で、1 枚目と同じく記憶を使わず点だけで切り抜き、以後の記憶に入れる。前のフレームには効かせない |

方式 B（SAM2 公式どおり、後ろの点を前のフレームにも効かせる）と C（点を打ったフレームで区切って別々に追跡）は採らない。
オーナーの判断: 激しく動く所にフレームを指定すれば、前後を補う仕組みは要らない。

## 3. 受け渡しの形

### 3.1 フレームの指定（prompt）

```json
{ "time_ms": 4300, "points": [{ "x": 0.51, "y": 0.44, "label": "include" }] }
```

- `time_ms`: 元の動画の時刻（ミリ秒、整数）。`range_ms` と同じ基準
- `points`: 今と同じ（1〜8 個、0.0〜1.0、`include` / `exclude`）

規則（Rust の送信・ワーカーの受け付けで同じ検査）:
- 1〜5 個。**1 つ目の `time_ms` は範囲の開始（`range_ms.start`）と等しい**（今の 1 枚目と同じ意味）
- `time_ms` は昇順で重複なし、`range_ms.start ≤ time_ms < range_ms.end`

### 3.2 ワーカーへの依頼（`contracts/video_cutout/worker_job_request.json`）

`prompts` を足す。移行のため `points`（= 1 つ目の prompt の点）も**残して送る**:
- 古いワーカーは知らないキーを無視するので、`points` だけ使って今どおり動く（2 枚目以降は効かないが壊れない）
- 新しいワーカーは `prompts` があればそれを使い、無ければ `points` を「開始位置の 1 つの prompt」として扱う

→ Cloud Run（Rust）と Modal（ワーカー）をどちらの順にデプロイしても動く。`points` を送るのをやめるのは別の変更で行う。

### 3.3 Rust の API（スマホとの間。同じサーバーが配信するので、古い形は受け付けない）

| ルート | 変更 |
|---|---|
| `POST /video-jobs/{id}/preview-frame?time_ms=4300` | クエリに `time_ms` を足す（必須）。その時刻のフレームとして特徴量を保存 |
| `POST /video-jobs/{id}/preview` | 本文に `time_ms` を足す（必須）: `{ "time_ms": 4300, "points": [...] }` |
| `POST /video-jobs/{id}/start` | `points` の代わりに `prompts`: `{ "prompts": [...], "background": "green" }` |

ルートは増えないので、利用ログ（`operation.rs` / `recorder.rs`）は変えない。

## 4. ワーカー

- `time_ms` → フレーム番号: `round((time_ms − range_ms.start) × fps ÷ 1000)`（fps は出力の fps = min(元, 30)）。
  同じ番号になる prompt が 2 つあれば、後のものを使う（ログに残す）。範囲外の番号は捨てる
- `VariantTracker.process(frame, points)`: 1 枚目だけでなく、**どのフレームでも points を受け付ける**。points があるフレームは
  - デコードは `feats2_no_mem`（記憶なし）と点で行う（1 枚目と同じ計算 = プレビューと一致）
  - メモリ化は `binarize=1`、そのフレームは**条件メモリ**になる（DAM4SAM の条件メモリの枠 = フレーム 0・DRM と同じ一覧）
  - DAM4SAM の DRM に足すかの判定はしない（利用者の指定なので無条件で条件メモリ）
- 被写体が見つからない（スコア ≤ 0）とき: 1 枚目は今どおり `subject_not_found` で失敗。2 枚目以降の指定フレームは「見失い」として数え、失敗にしない
- 体から離れた塊を消す後処理（`postprocess.py`、`REMOVE_DETACHED_BLOBS`）: 指定フレームには**かけず**、そのフレームの範囲で
  「前のフレームの範囲」を置き直す（`DetachedBlobFilter.reset(logits)` を足す）
- 本番の追跡は `VariantTracker`（DAM4SAM）だけ対応する。`tracker.py` の `Sam2VideoTracker` は計測の基準用なので 1 枚目だけのまま

## 5. Rust

- ドメイン: `job/prompt.rs` に `Prompt { time_ms: u32, points: Points }` と `Prompts`（3.1 の規則を `ClipRange` に対して検査する
  `Prompts::new(Vec<Prompt>, &ClipRange)`）。`MAX_PROMPTS = 5`。`VideoJob.points` → `VideoJob.prompts`
- 特徴量の保存（`PreviewFeatureStore`）: キーを `(VideoJobId, time_ms)` にする。1 ジョブ最大 `MAX_PROMPTS` 枚（6 枚目の時刻は
  409 `TOO_MANY_PREVIEW_FRAMES`）。全体の上限は今と同じ `MAX_PREVIEW_FEATURES = 16`（LRU は枚単位）。
  `remove(job)` はそのジョブの全部を消す。`retain_ids` も同じ
- `set_preview_frame`: `time_ms` が範囲の中かを検査（範囲外は 400 `INVALID_PREVIEW_TIME`）。それ以外は今と同じ
- `preview_mask`: `(job, time_ms)` の特徴量でデコード。無ければ今と同じ 409 `PREVIEW_FRAME_NOT_FOUND`
- `start_job`: `prompts` を検査（違反は 400 `INVALID_PROMPTS`）してジョブに保存し、ワーカーへの依頼に `prompts` と `points`（1 つ目）を入れる
- エラーは `common/macros.rs` のマクロで、leaf で HTTP ステータスとコードを決める（約束事）

## 6. スマホの画面（手順 4「残す所をタップ」）

- 開始位置のフレームを 1 枚目として表示（今どおり）
- 「**このフレームにも点を打つ**」ボタン: 押すと範囲の中で動かせる動画（シークバー）を出す。「このフレームに決める」で、
  その時刻のフレームを切り出して `preview-frame?time_ms=` で登録し、1 枚目と同じように点を打ってプレビューで確かめる
- 点を打ったフレームは、時刻の付いたタブ（例「0:00.0」「0:03.1」）で切り替える。フレームごとに点・Undo/Redo・プレビューを持つ。
  1 枚目以外は削除できる。5 枚で追加のボタンを無効にする
- 送信ボタンは、**すべてのフレーム**で点が 1 つ以上あり、被写体が見つかっている（`X-Object-Present: true`）ときだけ押せる
- 案内: 「カットのある動画は、カットの少し後のフレームにも点を打ってください」「腕が欠ける所は、そのフレームに点を打つと直ることがあります」
- 時刻のずれ: ブラウザの動画の位置とワーカーの数えるフレームは 1 フレーム（約 0.03 秒）ずれることがある。
  カットの直後を選ぶとカットの前の場面になる危険があるので、上の案内で「少し後」を勧める（自動の補正はしない）

## 7. テスト

- ワーカー: 契約（`prompts` あり・`points` だけの古い形・規則違反）、`time_ms` → フレーム番号、`VariantTracker` で指定フレームが
  記憶なしでデコードされ `binarize=1`・以後の条件メモリに入ること、パイプラインが指定フレームに点を渡し後処理を置き直すこと
- Rust: `Prompts` の規則、特徴量の保存（時刻ごと・1 ジョブ 5 枚・全体 16 枚の LRU・ジョブごとの削除）、各ユースケース、ルーター
- 契約: `contracts/video_cutout/worker_job_request.json` を Rust（送る側）と Python（受ける側）の両方のテストで読む（今の仕組み）
- 実モデル: カットのあるダーツの動画（元の 8.4 秒）で、開始位置とカットの少し後（約 0.4 秒）に点を打ち、見失いが 15 フレーム → 0〜2 フレームに減ること
- フロント: `frontend/js/video/selftest.html` の既存の自己テストに、タブの切り替え・送信の可否の判定を足す

## 8. やらないこと

- カットの自動検出、方式 B（後ろの点を前のフレームに効かせる）、プレビューでの 2 枚目以降の「追跡した結果」の表示
- 古いワーカー向けの `points` を送るのをやめること（両方のデプロイが済んでから別の変更で）
