## 判断基準

- **コールドスタート（送受信を除く推定）≤ 60 秒 → Modal で続行**
  - 送受信を除く推定 = コールドの差（手元の所要 − サーバー処理）− ウォームの差の平均。
    差には手元 PC からの動画のアップロードと出力 mp4 のダウンロードが入るが、本番のワーカーは R2 から取るので除く
  - あわせて「モデル読込」「起動→準備完了」の列も見る（Python が動く前のコンテナ起動分は差にしか現れない）
- 60 秒を超えたら Modal のメモリスナップショット（`enable_memory_snapshot`）を試して再計測する
- それでも超えるなら作業を止めてオーナーに報告する（RunPod への切り替えは計画の変更として扱う）

## 判断

- **コールドスタートは 150〜724 秒で、基準の 60 秒を大きく超えた。** ただしモデル読込は 1〜3 秒で、
  原因は Python が動く前（Pending = GPU の割り当て待ち、または大きな CUDA イメージの配布）にある。
- ウォームでの速度・精度・費用は目標を満たす（10 秒の動画でサーバー処理 約 18 秒、見失い 0、約 0.6 円）。
- 判断基準どおり作業を止めてオーナーに報告し、オーナーは「原因の切り分け」を選んだ（常時起動は月 約 $575 のため見送り）。
- **再計測の結果、コールドスタートは 5.3 秒（送受信を除く推定）で基準の 60 秒を満たした → Modal で続行する。**
- 本番も GPU は `["L4", "A10G", "T4"]` のフォールバックにする（L4 だけに絞ると割り当て待ちで数分〜10 分以上待たされる）。
  イメージは実ジョブで確認できた slim を使う。常時起動（min_containers）は不要。
- 費用は A10G / T4 に割り当たると単価が L4 と変わるが、1 本 数セント未満で 1 円未満の目標の範囲に収まる見込み（請求画面で要確認）。
- HDR の実機ファイルでの確認は未実施（4 本とも SDR だった）。

## 合成の改善（2026-11-07）

オーナーの踊っている動画（576x1024・300 フレーム）で、1 フレームあたりの緑かぶり（混色）画素の平均を本番で測った。

| 条件 | 緑かぶり画素 / フレーム |
|---|---|
| 元の柔らかい alpha（確率をそのまま使用） | 4573 |
| `EDGE_SHARPNESS=4` | 2206 |
| 完全に硬い合成を同じ libx264 yuv420p でエンコードし直した場合（下限） | 約 620 |

- 下限の約 620 画素は yuv420p のクロマ間引きによるもので、エンコード設定を変えない限り消せない。
  CapCut / iPhone / SNS との互換性のため yuv420p は維持する。
- 4 でも約 1600 画素/フレームは、ブレた領域で SAM2 のロジットが 0 付近に留まる半透明の alpha だった。
- そこで `EDGE_SHARPNESS` を 16 に上げた（alpha 0.05〜0.95 はロジット約 ±0.18 だけ。ロジット ±0.25 で alpha 約 0.02 / 0.98）。
  境界（ロジット 0 = alpha 0.5）の位置は動かない。残る約 1px の緑の縁はクロマ間引きによる。

## 速く動く手が消える原因の診断（2026-11-07）

`EDGE_SHARPNESS=16` の本番の出力で、胴体・脚は 300 フレームすべて追えている（見失いの 0 フレーム）が、
**速く振った前腕・手だけが消える**（手だけ宙に浮くフレームがある。60〜70 フレーム目など）。
`worker/scripts/diagnose_logits.py` でオーナーの PC（CPU）で同じ動画（`--start-ms 10700`、点 0.50,0.42）を処理した。
左のパネル（本番と同じ合成）は本番の出力と緑の領域の IoU 0.995 以上で一致（GPU と CPU の差は無視できる）。

ロジットが閾値を超える面積（512x512 の画素数、15 フレームおき。閾値 0 からの増加率）:
閾値 -2 で平均 +8%（最大 +24%、206 フレーム目）、閾値 -4 で +11〜29%（1 フレーム目だけ +89%）。

目視（ロジットの色分けと、閾値 -2 にずらした合成）:

- 消えた前腕のロジットは 0 の少し下ではなく、**まだらに -2 〜 -4 以下**。閾値 -2 でも腕は穴だらけでしか戻らない
- 閾値 -2 にすると、**後ろの同じ服の踊り手の腕や上着が混ざる**（206 フレーム目で顕著。1 フレーム目にも小片）
- 動画は同じ衣装の 5 人が重なって踊るもので、ブレた腕と、背後の同じ色の袖を SAM2 tiny が区別できていない

結論: **原因は合成ではなく、SAM2 tiny の識別（B）**。合成の閾値を下げると、別の人が混ざるので採らない。
`EDGE_SHARPNESS=16` は据え置く。補足: このモデルの入力は 512x512（公式の SAM2 は 1024）で、
576x1024 の縦長のフレームを 512 に縮めるため、腕は数画素の幅しかない。次の手は解像度（案 B）か、モデル（案 C）。

## 案 C: tiny と small の比較（2026-11-07）

`diffusionstudio` の SAM2.1 動画 ONNX は tiny / small / base-plus / large が同じ形式で公開されている
（5 グラフ・同じ constants.json の項目。違いは入力の解像度と画像エンコーダの大きさ）。
ワーカーの解像度の固定（512）をやめ、constants.json の `image_size` から決めるようにした（tiny の動きは変わらない）。

| モデル | 入力 | vision_encoder | memory_attention の memory | リビジョン |
|---|---|---|---|---|
| tiny（本番） | 512 | 58MB | 7,232 トークン | `66673b5d…` |
| small | 1024 | 84MB | 28,736 トークン | `927ecec6…` |
| base-plus | 1024 | 156MB | 28,736 トークン | `386b83e0…` |
| large | 1024 | 447MB | 28,736 トークン | `98dbd222…` |

CPU での速さ（開発環境の 4 コア、15 フレーム）: tiny 0.79 秒/フレーム、small 4.65 秒/フレーム（約 5.9 倍）。
GPU（Modal）での速さと費用は未計測。

同じ動画（`--start-ms 10700`、点 0.50,0.42、300 フレーム）を、オーナーの PC で small で処理して tiny と比べた（目視）:

- 腕が消えていたフレーム（60・66・206 番目）で、small はブレた前腕のロジットがはっきり正（色分けで赤）になり、
  **前腕が体とつながって残る**。tiny では同じ所が青（-2〜-4 以下）で、手だけが浮いていた
- 262 番目（手を前に突き出す）は両方ほぼ同じで良好
- small でも完全ではない: 206 番目の肘の近くに隣の人との境のギザギザ、数フレームで頭の横に小さな点が残る
- 「主成分から離れた 80 画素以上の塊があるフレーム数」は tiny 19 / small 19（塊の平均画素 39 → 22）。
  この指標では差が出ない（浮いた手より、小さなゴミの方を多く数えてしまう）ので、判断は目視による

結論（暫定）: small は今回の問題（速く動く腕が消える）に**目に見えて効く**。採用するかは GPU での処理時間と費用を測ってから決める。

オーナーの PC（CPU）で 300 フレーム: tiny 752 秒（2.51 秒/フレーム）、small 5416 秒（18.05 秒/フレーム、約 7.2 倍）。

**判断（オーナー、2026-11-07）: small は採らない**。処理時間とその分の費用が上がるため。本番は tiny のまま。
速く動く腕が消える（特に同じ服の人が重なる場面）のは、tiny の既知の限界として扱う。
ワーカーの「解像度を `image_size` から決める」変更と、診断スクリプトの `--model` は残す（tiny の動きは変わらず、将来の比較に使える）。

## 案 C: Modal の GPU での tiny と small（2026-11-08）

`worker/measure/measure_app.py --model tiny|small`（slim イメージ）で、同じ動画（D_man.mp4 の 10.7〜20.7 秒・300 フレーム、点 0.50,0.42）を処理した。
両方とも **NVIDIA A10** に割り当たった（同じ GPU で比べられた）。2 回ずつ、どちらもコールド扱い。

| 項目 | tiny | small | 倍率 |
|---|---|---|---|
| サーバー処理（10 秒の動画） | 14.1〜14.4 秒 | 38.8〜38.9 秒 | 約 2.7 倍 |
| 推論（tracker）1 フレーム 平均 / 中央値 | 28 / 23.5 ms | 110 / 105 ms | 約 4.5 倍 |
| 合成 + ロゴ 1 フレーム | 16 ms | 16 ms | 同じ |
| 推定費用（L4 単価での概算） | $0.0033〜0.0036 | $0.0088〜0.0093 | 約 2.6 倍 |
| モデル読込 | 0.8〜1.8 秒 | 0.8〜3.2 秒 | - |

- CPU では約 7 倍だったが、GPU では**処理全体で約 2.7 倍**（推論だけなら約 4.5 倍。デコード・合成・エンコードはモデルに関係しない）
- A10 の単価は L4 より高いので、A10 に当たった回の実際の費用は表より高い
- 呼び出し→コンテナ起動が 75〜95 秒と長いのは、計測が手元の PC から動画（21MB）を送るためと、イメージを作り直した直後のため。
  本番（R2 経由、コールドスタート 5.3 秒）とは比べられない。tiny と small で差は無い
- 合成 + ロゴが 1 フレーム 16ms（tiny ではサーバー処理の約 3 分の 1）。モデルに関係なく削れる余地がある

画質（オーナーの目視）: small は tiny より良い。ただし、ところどころ**被写体以外（同じ服の隣の人の肩や腕）を拾う**・**切り抜けていない所がある**。
この動画は同じ衣装の 5 人が重なって踊る、識別がいちばん難しい種類の動画。

## 案 C の続き: DAM4SAM・SAMURAI・base-plus（2026-11-08）

同じ動画・同じ点（0.50,0.42）、slim イメージ、4 本とも **NVIDIA A10**。サーバー処理（10 秒の動画）と推論 1 フレームの中央値:

| モデル / 記憶 | サーバー処理 | 推論（中央値） | small sam2 との比 |
|---|---|---|---|
| tiny / sam2（前回） | 14.1〜14.4 秒 | 23.5 ms | 0.37 倍 |
| small / sam2 | 38.2〜38.8 秒 | 104〜105 ms | 1 |
| small / dam4sam | 39.9〜41.4 秒 | 109〜112 ms | 約 1.05 倍 |
| small / samurai | 40.2 秒（2 回目 74.6 秒は外れ値） | 109 ms | 約 1.04 倍 |
| base-plus / sam2 | 46.5〜47.6 秒 | 134〜135 ms | 約 1.2 倍 |

- samurai の 2 回目は、デコード・合成・エンコードまで全部が約 2 倍遅く、推論の手法と関係ない工程も遅いので、
  割り当たった GPU（同じ機械の他の処理）の影響と見て外れ値にした
- DAM4SAM・SAMURAI の上乗せは 5% 前後（記憶の選び方の計算と候補マスクの出力の分）
- 画質（オーナーの目視）: **base-plus でも隣の人の腕を拾う**。DAM4SAM・SAMURAI の画質は未確認

画質（DAM4SAM・SAMURAI の出力の 2 回目を、small / sam2 と比べた。small / sam2 はオーナーの PC で作った診断の動画の左のパネル）:

| | 前景との違い（1 フレーム平均） | 体から離れた 80 画素以上の塊があるフレーム | 塊の平均画素 |
|---|---|---|---|
| small / sam2 | - | 19 / 300 | 22 |
| small / dam4sam | 538 画素（前景の約 1%） | 13 / 300 | 13 |
| small / samurai | 532 画素（前景の約 1%） | 23 / 300 | 52 |

- 違いは前景の約 1% で、CPU と GPU の計算の差（tiny で IoU 0.995 程度）と同じくらいしかない
- 目視（差が大きかった 34・47・195・206 フレーム目）: DAM4SAM は小さな離れた点が少し減る。SAMURAI は 206 フレーム目の腕の
  つながりがやや良いが、離れた塊は増える。どちらも**隣の人を拾う問題を解消するほどの差は無い**
- 結論: 同じ衣装の人が重なる動画では、モデルの大型化（base-plus）も、記憶の選び方（DAM4SAM・SAMURAI の再現）も効かない
